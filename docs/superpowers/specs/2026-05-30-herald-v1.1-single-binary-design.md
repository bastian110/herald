# Herald v1.1 — Single Binary + Subcommands Design

**Date:** 2026-05-30
**Status:** Approved (direction); spec under review

## Motivation

v1 ships the daemon plus three Bash scripts (`herald-send`, `herald-recv`,
`herald-pi-bridge`) that depend on `socat` + `jq`. That layer is fragile: the
stdin-consumption bug and JSON quoting-by-hand both came from it. v1.1 folds the
client primitives into the Go binary so there are **no external runtime
dependencies** for talking to herald, and rewrites the per-harness bridges as
trivial scripts on top of those primitives.

**What stays the same:** the daemon's behaviour, the wire protocol, the socket,
and the design principle that **bridges are harness-specific** (each harness has
its own agent commands). v1.1 does *not* introduce a generic bridge.

## Architecture

```
herald (single Go binary)
├── herald serve          daemon: poll Telegram, broadcast, forward   (= v1 main)
├── herald send "msg"     primitive: write a send op, read the ack
└── herald recv           primitive: read inbound message(s)
                          --follow  stream every message (for bridges)
                          --json    emit the raw envelope
                          --timeout give up after N seconds

per-harness bridges (thin shell, built on the primitives — no socat/jq)
└── bin/herald-pi-bridge  herald recv --follow | run pi | herald send
```

The binary carries everything **generic** (transport + client primitives). Each
**bridge stays specific** to its harness but becomes trivial: read with
`herald recv --follow`, reply with `herald send`. No socket plumbing, no JSON
parsing, no stdin pitfalls.

## Command Dispatch

`main()` dispatches on `os.Args[1]` to one of three subcommands; no third-party
CLI library (stdlib `flag` per subcommand). Unknown/empty → usage to stderr,
exit 2.

```
herald serve
herald send [--socket PATH] [--chat-id N] <text>
herald recv [--socket PATH] [--follow] [--json] [--timeout SECONDS]
```

`--socket` defaults to `$HERALD_SOCKET` then `/tmp/herald.sock`.

### `herald serve`

Exactly the current v1 daemon (the existing `run()` in `cmd/herald/app.go`),
moved behind the subcommand. Same env vars (`TELEGRAM_BOT_TOKEN`,
`HERALD_SOCKET`, `HERALD_POLL_TIMEOUT`, `HERALD_CHAT_ID`).

### `herald send`

1. Dial the socket (error `herald send: daemon not running at <path>`, exit 1).
2. Write `{"op":"send","text":<text>,"chat_id":<n?>}` + newline.
3. Read one reply line. `ack` → exit 0. `error` → print message to stderr, exit 1.

`--chat-id` is optional; omitted means the daemon's default chat.

### `herald recv`

- **One-shot (default):** dial, read exactly one `message` line, print it, exit 0.
  `--timeout N` → exit 1 with a timeout message if nothing arrives in N seconds.
- **Follow (`--follow`):** dial once and keep the connection open, printing each
  inbound `message` as it arrives, until the connection closes or the process is
  killed. This is what bridges use — herald buffers up to 16 messages per
  subscriber, so messages arriving while the bridge's agent is busy are not lost.
- **Output:** default prints `.text` only (one line per message). `--json` prints
  the raw envelope line (for bridges that need `from`/`chat_id`).

Default text-only output means a single-chat bridge needs **no `jq`** at all.

## Shared Client Package

New `internal/client` package holds the socket logic used by both `send` and
`recv`, so the subcommands stay thin:

```go
package client

// Dial connects to the herald Unix socket.
func Dial(socketPath string) (net.Conn, error)

// Send writes a send op and returns the daemon's ack/error envelope.
func Send(socketPath string, text string, chatID int64) (protocol.Envelope, error)

// Recv reads message envelopes from the socket and calls handle for each one.
// If follow is false it returns after the first message. A zero timeout means
// no timeout. Returns context/timeout errors to the caller.
func Recv(socketPath string, follow bool, timeout time.Duration, handle func(protocol.Envelope) error) error
```

This reuses the existing `internal/protocol` envelope — no new wire types.

## The pi Bridge, Rewritten

`bin/herald-pi-bridge` drops `socat`/`jq` entirely:

```bash
#!/usr/bin/env bash
set -uo pipefail
S="${HERALD_PI_SESSION_DIR:-$HOME/.herald/pi-sessions}"
W="${HERALD_PI_WORKDIR:-$HOME}"
mkdir -p "$S"

herald recv --follow | while IFS= read -r text; do
  [[ -n "$text" ]] || continue
  if [[ "$text" == "/new" ]]; then
    rm -rf "$S"/* 2>/dev/null
    herald send "🔄 Nouvelle conversation pi (contexte agent reset)."
    continue
  fi
  reply=$(cd "$W" && pi --session-dir "$S" -c -p "$text" </dev/null 2>&1)
  [[ -n "$reply" ]] || reply="(pi: réponse vide)"
  herald send "$reply"
done
```

Notes:
- Replies go to the daemon's default chat (`HERALD_CHAT_ID`); single-user setups
  need nothing more. A multi-chat bridge would use `herald recv --follow --json`
  and pass `--chat-id`.
- The `</dev/null` stdin guard stays (pi reads stdin when not a TTY).
- `/new` clears the isolated session dir; the next message starts fresh.

> Writing a bridge for another harness (claude, a homemade agent) is the same
> three lines: `herald recv --follow` → run the agent → `herald send`. The bridge
> stays specific to that harness's commands; only the plumbing is shared.

## Backward Compatibility

This is a breaking change to the *invocation* (`./herald` → `herald serve`,
`herald-send` → `herald send`). The wire protocol and socket are unchanged. The
systemd unit's `ExecStart` is updated. No data migration needed.

## Testing

- `internal/client`: unit tests for `Send` (ack + error paths) and `Recv`
  (one-shot, follow delivering multiple, timeout) against a throwaway socket
  served by `internal/socket`.
- `cmd/herald`: dispatch test (unknown subcommand → exit 2); keep the end-to-end
  mock-Telegram test, launched via the `serve` path.
- Manual: `herald serve` + `herald send` + `herald recv --follow` smoke test, then
  the pi bridge live.

## Out of Scope (v1.1)

- Generic/parameterised bridge (`herald bridge -- <cmd>`) — explicitly rejected;
  bridges stay harness-specific.
- New platforms (WhatsApp/Signal), message persistence, multi-agent routing.
